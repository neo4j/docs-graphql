= Entity API and connections API
:description: This page introduces the entity and connections APIs and aims to shed light on their differences, when to use which API and how they can be mixed in practice.

The xref:index.adoc[introduction] or one of the xref:getting-started/index.adoc[getting started] pages touch on the topic of auto-generated fields exactly the GraphQL Library generates based on the type definition schema that you provide.

It is a pair of distinct APIs that you can explore with the Apollo Server.
Examples drawing from the auto-generated fields of the two APIs are used throughout the GraphQL Library documentation, but the difference and separation of them is implicit.


== Distinction

The API split is mainly due to development-historic reasons.
The entity API came first and is simpler and more performant, while the connections API allows for relationship traversal, accessing relationship fields, aggregations and more.
Knowing the difference allows you to make a more deliberate choice of when to use which API.

Consider the following type definitions:

[source, graphql, indent=0]
----
type Movie @node {
    title: String!
    released: Int
    actors: [Person!]! @relationship(type: "ACTED_IN", direction: IN, properties: "ActedInProps")
}

type Person @node {
    name: String!
    movies: [Movie!]! @relationship(type: "ACTED_IN", direction: OUT, properties: "ActedInProps")
}

type ActedInProps @relationshipProperties {
    roles: [String!]!
}
----

The following sections outline the entity and connections APIs that are generated based on the definitions.

[NOTE]
====
To explore the different fields outlined on this page yourself, put the type definitions in a JavaScript file and fire up an Apollo server as explained in the xref:getting-started/graphql-self-hosted.adoc[Self-hosting GraphQL] guide.
====


== Entity API

The entity API provides the following fields for the `Movie` and `Person` `@node` types:

[source, text, indent=0]
----
movies(...): [Movie!]!

people(...): [Person!]!
----

Each entity can take four arguments:

* `where`
* `limit`
* `offset`
* `sort`

The `where` and `sort` arguments can be used to filter and sort query results.
Refer to xref:filtering.adoc[] and xref:sorting.adoc[].
`limit` and `offset` allow for xref:queries-aggregations/pagination.adoc#pagination-offset-based[offset-based pagination].

`Movie` and `Person` entities are connected via the `ACTED_IN` relationship.
`Movie` types have a field `actors` that is a list of `Person` entities, while `Person` entities have a field `movies` that is a list of `Movie` entities.
This means that you can access other entities directly from an entity that is connected to them.

Note that alongside the `actors` field (for `Movie` entities) and the `movies` field (for `Person` entities) you can also access the fields `actorsConnection` and `moviesConnection` respectively.
These fields are provided by the connections API, not the entity API.
You can mix both APIs at certain levels in the same query.

A `Movie` entity also allows you to access the `title` and `released` fields, while a `Person` entity allows you to access its `name` field.

For example:

[source, graphql, indent=0]
----
query EntityApi {
  movies(limit: 10, offset: 5) {
    title
    released
    actors(limit: 2) {
      name
    }
  }
}
----

== Connections API

The connections API follows a different approach.
For each entity identified in the schema, it creates a connection field:

[source, text, indent=0]
----
moviesConnection(...): MoviesConnection!

peopleConnection(...): PeopleConnection!
----

Each connection can take four arguments:

* `first`
* `after`
* `where`
* `sort`

While `where` and `sort` are used to xref:filtering.adoc[filter] and xref:sorting.adoc[sort] query results similarly to the entity API, `first` and `after` describe a pagination cursor that you can use in subsequent queries (see xref:queries-aggregations/pagination.adoc#pagination-cursor-based[cursor-based pagination]).

Connections fields can access the following:

* `aggregate`
* `edges`
* `pageInfo`
* `totalCount`

For examples on how to use the `aggregate` field, refer xref:queries-aggregations/aggregations.adoc#_querying_aggregations[].

`edges` represent a set of relationship connections.
They let you access the fields `cursor`, which is the pagination cursor, and `node`, which makes the corresponding field provided by the entity API accessible.
This means that you can at this level mix in the entity API while you are using the connections API.


Nested connections also let you access the relationship properties via the field `properties`.
This does not work with top-level connections.

For example:

[source, graphql, indent=0]
----
query ConnectionApi {
  moviesConnection(first: 10) {
    edges {
      node {
        title
        actorsConnection {
          edges {
            node {
              name
            }
            properties {
              roles
            }
          }
        }
      }aggregation.a
      cursor
    }
    aggregate {
      node {
        title {
          longest
        }
      }
    }
  }
}
----

Note how `actorsConnection` is available under `moviesConnection.edges.node`, which is different from the top-level `peopleConnection`.
It's a nested connection and lets you access the relationship property `roles`.

`pageInfo` has the fields `startCursor`, `endCursor`, `hasPreviousPage` and `hasNextPage` which are used for xref:queries-aggregations/pagination.adoc#pagination-cursor-based[pagination].

Finally, `totalCount` is the number of connection items.
